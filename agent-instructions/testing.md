# Правила тестирования и проверок

## Справочная документация

[Официальная документация Vitest](https://vitest.dev/guide/) — используй при выборе API и настройке тестов. Учитывай версию Vitest в проекте и соблюдай соглашения этого документа.

## Общие требования

- обеспечивай проверку результата: каждое изменение должно быть проверено;
- запускай существующие тесты, покрывающие затронутое поведение; дополняй их, если нужный сценарий не проверяется;
- при исправлении бага сначала добавь регрессионный тест и убедись, что он падает по причине исправляемой ошибки; после исправления тест должен проходить;
- новое или изменённое поведение покрывай тестами в рамках той же задачи;
- если автоматический тест невозможно или нецелесообразно добавить, объясни причину, выполни доступную альтернативную проверку и укажи, что осталось непроверенным;
- если тесты или сборку нельзя запустить — прямо сообщи об этом;
- не утверждай, что код работает, без фактической проверки;
- в итоговом ответе указывай выполненные проверки и их результат, а для невыполненных — причину;
- при изменениях только в документации проверяй ссылки, команды и соответствие проекту; запуск тестов приложения не обязателен.

## Команды проверок

Проверка типов:

```bash
npm run typecheck
```

Линтинг и проверка форматирования:

```bash
npm run lint
```

Production-сборка:

```bash
npm run build
```

Тесты:

```bash
npm run test
```

Только unit-тесты:

```bash
npm run test -- test/unit/
```

Один файл тестов:

```bash
npm run test -- test/unit/domain/item-status.test.ts
```

Тесты по имени (пример выбирает один тест):

```bash
npm run test -- test/unit/domain/item-status.test.ts -t 'calculates item counts by status'
```

## Структура тестов

- Unit-тесты размещаются в `test/unit/`, повторяя структуру `src/`.
- Интеграционные тесты размещаются в `test/integration/` и группируются по проверяемой области или интеграции.
- Файлы тестов называются `<объект-проверки>.test.ts`: для unit-тестов это имя модуля, для интеграционных — имя проверяемого компонента или взаимодействия.
- Связанные сценарии одного объекта проверки размещаются в одном файле.
- Тестовые данные и хелперы располагаются рядом с тестами. Общие файлы выделяются при реальном повторном использовании внутри соответствующего набора.
- Тесты должны запускаться независимо.

## Соглашения о написании тестов

### Общие правила

1. **Группировка.** `describe` указывает проверяемую функцию, класс, компонент или интеграцию: `describe('answerTrainingItem', ...)`.

2. **Названия.** Названия тестов пишутся на английском: ожидаемое поведение, затем условие, если оно необходимо. Название начинается с глагола: `returns`, `creates`, `saves`, `updates`, `calculates`. Для проверок ошибок синхронных и асинхронных функций используется единый шаблон `throws error when ...`.

3. **Проверка ошибок.** Синхронные исключения проверяются через `.toThrow`, отклонения `Promise` — через `.rejects`.

4. **Структура.** В каждом тесте используется паттерн AAA: последовательно идут подготовка данных, вызов функции и проверка результата. Эти части разделяются пустыми строками. Очевидные действия не требуют поясняющих комментариев.

5. **Объём сценария.** Один тест проверяет один сценарий. Несколько `expect` допустимы, если вместе проверяют его результат: например, возвращённое значение, сохранённый ответ и обновлённый прогресс.

6. **Подготовка данных.** Каждый тест подготавливает необходимые ему данные и получает независимое изменяемое состояние. Даты и случайность задаются явно. Значимые числа, например число симуляций или порог сдачи, оформляются как константы с понятными именами.

7. **Параметризация.** Используй `it.each`, чтобы не дублировать тесты, отличающиеся только входными данными и ожидаемым результатом. Если для отдельных случаев нужны ветвления внутри теста — напиши отдельные тесты.

8. **Каркас.** Для незавершённых сценариев используется `it.todo` с полноценным названием по тем же правилам. TODO не считается реализованной проверкой.

9. **Очистка ресурсов.** Каждый тест должен освобождать созданные ресурсы и восстанавливать изменённое состояние, в том числе при падении. Закрывай подключения и серверы, удаляй временные файлы, отменяй таймеры и подписки, восстанавливай переменные окружения, глобальное состояние и моки. Для ресурсов, общих для набора тестов, выполняй очистку после завершения набора.

10. **Независимость.** Каждый тест должен запускаться самостоятельно и не зависеть от порядка выполнения или данных других тестов. При параллельном запуске изолируй данные и ресурсы. Если ресурсы нельзя использовать параллельно, явно настрой последовательное выполнение соответствующего набора; это не отменяет требования независимости тестов.

### Unit-тесты

1. **Изоляция.** Тесты выполняются без обращения к реальной БД, сети и внешним сервисам.

2. **Доменная логика.** Тесты проверяют результат функции, бизнес-правила и необходимые ограничения, например отсутствие изменения входного массива.

3. **Use-case.** Используются репозитории в памяти. Тесты проверяют возвращённый результат и сохранённые данные. При ошибке проверяются её тип, код и отсутствие недопустимых изменений. Все варианты доменного алгоритма повторно не перебираются.

### Интеграционные тесты

1. **Границы проверки.** Тест проверяет взаимодействие компонентов с реальными зависимостями внутри выбранной интеграции. Не подменяй моками проверяемое взаимодействие: например, при проверке репозитория с PostgreSQL используй реальный репозиторий и PostgreSQL. Зависимости вне границ проверки можно подменять.

2. **Тестовая БД.** Для тестов с БД используй отдельную тестовую базу с актуальными миграциями проекта. При очистке или откате учитывай изменения, выполненные через все соединения тестируемого кода.

3. **Результат.** Проверяй наблюдаемый результат взаимодействия: сохранённые данные, связи, ограничения БД и согласованность изменений при ошибках. Не дублируй все варианты бизнес-правил, уже покрытые unit-тестами.
